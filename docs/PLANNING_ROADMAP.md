# Tether — Planning Roadmap (2인 팀 최적화)

> **목적**: 2인 팀이 코드 이전 단계를 논리적으로 밟기 위한 로드맵.
> **원칙**: 시간 기반 X (1주/2주 등), **논리적 의존성 기반 O**.
> **작성**: 2026-07-24 (방향 재정립 직후)

---

## 🧭 2인 팀 기획 원칙 (전제)

1. **오버 프로세스 금지** — 대기업 게임 스튜디오 프로세스 X. 우리는 소통이 즉시라 문서 최소화 가능.
2. **라이브 우선** — 큰 결정은 디스코드 보이스 (30~60분 세션). 텍스트/문서는 라이브 결과 반영.
3. **문서는 필수만** — 반년 뒤 자기 자신이 봐도 이해할 수준. 그 이상은 낭비.
4. **병렬 가능은 병렬** — 두 사람 다 대기 상태 X. 스테이지 내에서 담당 분리.
5. **결정 없이 실행 O** (일부는) — 실험이 결정을 낳기도 함. 프로토타입이 컨셉을 다듬는 경우 많음.
6. **Iteration은 자유** — 뒤 스테이지에서 앞 결정이 흔들리면 돌아옴. 정상.

# Stage 1 — Vision Alignment 🎯 지금 여기

## 목표
**두 사람이 같은 게임을 상상하고 있는가?** 코드도, 시스템도, 아트도 아닌 *영혼* 합치기.

## 결정 필요 사항

### 1.1 Elevator pitch (한 문장으로 이 게임은?)
- Ball x Pit의 어떤 부분 + 동방의 어떤 부분 + 우리만의 어떤 부분 = ?
- 예: *"동방 캐릭터들이 하쿠레이 신사를 지키는 아르카노이드 로그라이트."*
- 이 문장 하나가 나머지 모든 결정의 기준

### 1.2 Core fantasy (플레이어가 뭘 느껴야 하나?)
- Ball x Pit: "약함 → 강함 → 게임 브레이커" 성장의 쾌감
- 동방: "환상향 캐릭터들과 함께" 팬 서비스
- 우리 게임의 감정선 축은?
  - 파워 판타지?
  - 팬 서비스?
  - 창의적 실험?
  - 도전의 만족?

### 1.3 레퍼런스 가중치
- Ball x Pit 몇 % 오마주?
- 동방 몇 % 팬 서비스?
- 우리만의 몇 % 오리지널?
- 예: 70% Ball x Pit 메카닉 + 20% 동방 캐릭터/스토리 + 10% 오리지널 트위스트

### 1.4 상업화 정책
- 팬 프로젝트 (무료 배포, GitHub/itch.io)
- 저가 유료 (동인 관례, ZUN 가이드라인 내)
- 오리지널 전환 (동방 요소 뺌, 상업 자유)
- **미정 유지** (프로토타입 후 판단)도 유효 선택

### 1.5 완성 목표 지점
- 프로토타입만 (1 스테이지, 폐기 가능)
- Steam 출시 (동인/저가)
- 무료 팬 게임 배포
- 진지한 상업 (오리지널 전환 후)

## 산출물
- **`docs/VISION.md`** (1~2 페이지)
  - 위 5가지 결정 정리
  - "이 게임이 아닌 것" 리스트 (Anti-Vision) 포함
  - 두 사람 다 사인 (문서 마지막에 합의 확인)

## 협업 방식
- **디스코드 라이브 세션 (60분)** — 첫 기획 세션
- 사전 준비:
  - 각자 5개 결정에 대한 자기 답 미리 생각
  - Ball x Pit 분석 문서 훑기 (docs/references/BALL_X_PIT_ANALYSIS.md)
  - 참고 게임 몇 개 자기 취향 정리
- 세션 후: 한 사람이 VISION.md 초안 → 상대 리뷰 → merge

## 완료 신호
> **"우리 게임은 ___이다"** 문장을 두 사람 다 즉시 말할 수 있음.

## Skip / Defer 가능?
❌ **불가능.** 이거 없이 다음 스테이지 진행하면 이후 계속 어긋남.

# Stage 2 — IP & Content Scoping

## 목표
동방 IP를 실제로 어떻게 다룰지 확정.

## 결정 필요 사항

### 2.1 동방 원작 스코프
- 어느 작품 중심? (제6작 홍마향 / 제7작 요요몽 / 제8작 영야초 / 전체 등)
- 최신작까지 커버 vs 클래식만
- 팬 창작에서 자주 쓰이는 라인 (홍마향 캐릭터가 인기 최고)

### 2.2 캐릭터 로스터 크기
- 시작 로스터 (플레이 가능 캐릭터 몇 명?)
- 확장 계획 (Phase 2, 3에 추가할 캐릭터)
- Ball x Pit 21명은 스케일 크니 우리는 초기 3~5 정도

### 2.3 캐릭터 선정
- **필수 후보** (거의 확실): 하쿠레이 레이무, 키리사메 마리사 (동방 2대 상징)
- **강력 후보**: 이자요이 사쿠야, 야쿠모 유카리, 스카알렛 자매, 알리스 마가트로이드
- **덕질 캐릭터** (각자 취향 우선): kimringo 취향 + 본인 취향 반영

### 2.4 오리지널 캐릭터?
- 완전 원작 캐릭터만 → 안전, 팬 서비스
- 오리지널 1~2명 추가 → 스토리 자유도 ↑, 팬 반응 조심
- 오리지널 조연 (원작 캐릭터 주연 + OC 조연) → 균형

### 2.5 스토리 프레임
- 원작 표준 이변 (누가 이변 일으킴 → 레이무/마리사가 해결)
- 오리지널 이변 (우리가 만든 상황)
- 스토리 최소 (아케이드 로그라이트, 스토리는 flavor)

### 2.6 세계관 위치
- 하쿠레이 신사 (환상향 심장, 가장 자연스러움)
- 인간 마을
- 새 오리지널 장소 (환상향의 발견 안 된 지역 등)

### 2.7 ZUN 가이드라인 준수 라인
- 완전 준수 (무료 팬 프로젝트)
- 관례적 라인 (Comiket 저가 유료 수준)
- 오리지널 전환 (동방 요소 이름/외형 다 바꿈)

## 산출물
- **`docs/IP_SCOPE.md`**
  - 동방 원작 스코프
  - 캐릭터 로스터 (초기 + 확장 계획)
  - 스토리 프레임
  - 세계관 위치
  - ZUN 가이드라인 방침

## 협업 방식
- **디스코드 라이브 세션 (30~60분)**
- 사전: 각자 동방 어느 캐릭터 좋아하는지, 왜 그런지 정리 (덕력 공유)
- 세션에서: 필수 + 취향 우선 캐릭터 결정
- 세션 후: 한 사람이 IP_SCOPE.md 초안 → 상대 리뷰

## 완료 신호
> **"이 게임에 등장하는 캐릭터 이름 5개 이상을 두 사람 다 즉시 나열 가능."**
> **"이 게임의 스토리는 ___에 관한 것이다"** 문장 합의.

## Skip / Defer 가능?
🟡 **일부 defer 가능** — 세계관 상세는 진행하며 다듬을 수 있음. 근데 캐릭터 로스터는 여기서 확정 필요 (아트 방향과 직결).

# Stage 3 — Core Gameplay Design

## 목표
**게임의 코어 루프 정의.** 매 런 뭐 하는지 명확화.

## 결정 필요 사항

### 3.1 뷰 / 카메라
- Ball x Pit 정면 아레나 (top-down 세로 스크롤) — 가장 검증됨
- 정면 고정 아레나 (스크롤 없음)
- 다른 시점 (탑다운 방사형, 사이드뷰 등) — 컨셉이 명확하면

### 3.2 코어 루프 상세
- 한 런 흐름을 다이어그램으로:
  ```
  스테이지 진입 → 웨이브 1 → 볼 획득 → Level up → 웨이브 2 
  → Fusion 기회 → 웨이브 3 → Stage Boss → 리워드 → 다음 or 종료
  ```

### 3.3 승리 조건 (한 런의)
- Ball x Pit식: 스테이지 클리어 (모든 웨이브 + 보스)
- Vampire Survivors식: 시간 버티기 (X분)
- 하이브리드

### 3.4 패배 조건 (사망)
- HP 0
- 시간 초과
- 특정 오브젝트 파괴됨 (신사가 부서지면 패배 등)

### 3.5 사망 페널티
- 진행 전부 리셋 (Ball x Pit식)
- 부분 리셋 (자원 일부 유지 등)
- 없음 (죽어도 계속)

### 3.6 시간 프레임
- 한 런: 몇 분 목표? (Ball x Pit: 20분)
- 한 세션 (게이머가 한번 앉음): 몇 분?
- 한 스테이지 클리어: 몇 런 필요?

## 산출물
- **`docs/CORE_LOOP.md`**
  - 게임 흐름 다이어그램 (ASCII or 그림)
  - 각 상태 설명
  - 승리/패배 조건
  - 시간 프레임 명시

## 협업 방식
- 각자 초안 (혼자, 자기 상상 그림)
- 디스코드에서 비교/합의
- 한 사람이 최종 문서 작성

## 완료 신호
> **CORE_LOOP.md의 다이어그램을 보고 두 사람이 "그래, 이거 맞다" 동의.**

## Skip / Defer 가능?
❌ **불가능.** 코드 진입 전 무조건 확정.

# Stage 5 — Art & Sound Direction (Stage 4와 병렬)

## 목표
게임의 룩/사운드 방향 확정.

## 결정 필요 사항

### 5.1 팔레트
- 전체 색 컨셉 (밝음/어두움, 채도, 대비)
- 각 biome별 팔레트 (환경 그라데이션)
- UI 색 (HUD, 메뉴)

### 5.2 캐릭터 아트 스타일
- 픽셀아트 (해상도, 프레임 수)
- 애니메이션 픽셀 (부드러운 애니, Sea of Stars 라인)
- 손그림 스타일 (Hollow Knight 라인)
- 동방 원작 팬아트 라인 vs 오리지널 해석

### 5.3 배경 / 환경 스타일
- 정적 배경 vs 애니메이션 배경
- 시대감 (전통 일본 vs 판타지 vs 혼합)

### 5.4 UI 디자인
- 폰트
- 프레임/버튼 스타일
- 이펙트

### 5.5 이펙트 / 파티클
- Ball 이펙트 (트레일, 폭발, 흡수)
- 스킬 이펙트 (스펠카드 발동)
- 환경 파티클 (분위기)

### 5.6 사운드
- SFX 스타일 (아케이드, 리얼, 판타지)
- BGM 장르 (동방 어레인지, 오케스트라, 칩튠, 록)
- 동방 원작 BGM 사용 여부 (ZUN 가이드라인)

# Stage 6 — Prototype Scope

## 목표
**MVP 정의.** 뭐가 되면 "굴러간다"인지 명확화.

## 결정 필요 사항

### 6.1 프로토타입 목표
- 무엇을 검증할 것인가?
  - Ball 발사/튐/충돌 재미 있음?
  - Fusion 시스템 이해 쉬움?
  - 동방 캐릭터로 하니 감성 살아남?
  - 웨이브 밸런싱 대략 감?

### 6.2 포함할 것 (Include)
- 시스템 리스트 (Stage 4에서 발췌)
- 콘텐츠 리스트 (캐릭터 1명, 볼 10종, 웨이브 3회 등)

### 6.3 제외할 것 (Exclude)
- 스킵 가능한 시스템 (메타, 세이브 등)
- 스킵 가능한 콘텐츠 (다중 캐릭터, 다중 스테이지 등)
- **명시적 제외 리스트가 없으면 스코프 폭발**

### 6.4 성공 기준
- "이 조건이 충족되면 다음 Phase로"
- 예: "10분 플레이 후 '다시 하고 싶다' 느낌"

### 6.5 실패 기준
- "이 조건이면 방향 폐기"
- 예: "3번 플레이 후 지루함 압도"

## 산출물
- **`docs/PROTOTYPE_SCOPE.md`**
  - Include / Exclude 리스트
  - 성공 / 실패 기준
  - "이 프로토타입으로 X를 검증한다" 명시

## 협업 방식
- 라이브 세션 (30~60분)
- 각자 "꼭 넣어야 함" vs "빼도 됨" 리스트
- 합의로 절충

## 완료 신호
> **Include 리스트에 있는 것만으로 게임이 "굴러간다"고 느껴짐.**

## Skip / Defer 가능?
❌ **불가능.** Task Breakdown 전 무조건 필요.

# Stage 7 — Task Breakdown

## 목표
실행 가능한 작업 단위로 쪼갬.

## 결정 필요 사항

### 7.1 시스템별 Task 분해
- 각 Include 시스템을 실행 가능한 task로
- Task 크기 목표: 하루 이내 완료 (2인 팀 리듬)
- Dependency 명시 (이 task 전에 저 task 필요)

### 7.2 우선순위
- Critical path 식별
- Blocking task 우선

### 7.3 담당 배정
- 파트 분담에 따라 각자 자기 파트
- 크로스 리뷰 (상대가 최종 리뷰)

### 7.4 트래킹 도구
- GitHub Issues + Projects (권장)
- 또는 Notion, Trello 등

## 산출물
- **GitHub Issues** (여러 개, 각 task마다)
- **GitHub Project board** (칸반 or 스프린트)
- **`docs/PHASE_1_BACKLOG.md`** (요약 인덱스)

## 협업 방식
- 라이브 or 비동기 (자유)
- 초기 세팅은 라이브 (기준 잡기)

## 완료 신호
> **각자 "지금 뭐 만들어야 하지?" 물으면 즉시 답 나옴.**

## Skip / Defer 가능?
❌ **불가능.** 실제 개발 전 무조건 필요.

# Stage 8 — Iteration Cadence

## 목표
실제 개발 중 어떻게 리듬을 잡을지.

## 결정 필요 사항

### 8.1 스프린트 / 사이클
- 스프린트 길이 (1주? 2주? 논리적 단위?)
- 스프린트 리뷰 시점
- 백로그 재정렬 주기

### 8.2 리뷰 리듬
- PR 리뷰 SLA (얼마나 빨리)
- 큰 결정 리뷰 (디스코드 세션 주기)

### 8.3 데모 / 플레이테스트
- 자체 데모 (매 스프린트 끝?)
- 외부 플레이테스트 (누구에게, 언제)

### 8.4 밸런싱 세션
- 밸런싱 수치 튜닝 주기
- 데이터 수집 방법

## 산출물
- **`docs/DEVELOPMENT_WORKFLOW.md`** (또는 SETUP.md 확장)

## 협업 방식
- 라이브 (30분)
- 개발 진행하며 자연스럽게 형성돼도 OK

## 완료 신호
> **매주 어떻게 진행되는지 두 사람 다 같은 상 있음.**

## Skip / Defer 가능?
